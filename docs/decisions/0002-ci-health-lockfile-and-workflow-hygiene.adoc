= ADR-0002 — CI health: `actions.lock` is authoritative, and the workflow gates must agree with it
:revdate: 2026-10-04
:status: ACCEPTED

== Context

open pull request:

Three of these are not independent faults. They are one fault wearing three
hats, and it is worth naming it precisely, because it is the thing that
recurs.

=== The core matter: `actions.lock` is authoritative, and nothing kept it so

This repository's pinning model was settled by two commits that disagree with
each other:

* `c30a7fb` (#73, 2026-09-20) — "pin third-party actions to full commit SHAs",
  on the stated ground that the account's Actions policy refuses a tag or
  branch ref at startup (`startup_failure`, no jobs, "this workflow graph
  cannot be shown"). It SHA-pinned every ref inline.
* `cfc1b50` (#74, 2026-09-20, three hours later) — "reconcile the workflows
  with actions.lock", which *reverted* those inline SHAs back to readable refs
  on the ground that "`actions.lock` is authoritative: the workflows carry
  readable refs and the lock records the commit each ref resolves to, which is
what actually runs. Refs that stop matching the manifest make the whole
repository unstartable — `startup_failure`, 'Invalid lockfile'."

#74 is the correct model and #73's premise is wrong for this repository — the
workflows demonstrably do run on tag refs today. But #74 fixed the *symptom*
and left the *mechanism* missing: nothing in this repository verified that the
lockfile still matched the workflows. The estate's own drift checker spells out
why that matters:

****
Dependabot bumps an action version *in a workflow file*. Nobody regenerates
`.github/workflows/actions.lock`. The workflow now requests a version the
lockfile does not record, and GitHub rejects the run at `startup_failure` with
ZERO jobs — no log, no annotation, nothing in REST or GraphQL. It is
self-reinflicting: any repo with Dependabot AND a lockfile AND no regeneration
step re-acquires the fault on every action bump.
****

That is exactly what happened here, three times:

[cols="1,1,1"]
|===
|Commit |Effect on `codeql.yml` |`actions.lock` after

|`5977b22` (#79, 2026-09-21)
|`github/codeql-action@v4.38.0`
|`v4.38.0` — in step, CodeQL green
|`28c32d3` (#78, 2026-09-26)
|`v4.38.1` (dependabot)
|still `v4.38.0` — **drift**, CodeQL red from here on
|`6c1bf2d` (#83, 2026-10-03)
|`v4.38.2` (dependabot)
|still `v4.38.0` — **drift**, CodeQL red
|===

The failure signature matches the diagnosis exactly. Every other workflow in
the repository kept running, because every other workflow's refs still matched
the lock. Only `codeql.yml` had drifted, so only `CodeQL Advanced` died. The
run list confirms it: 100% `startup_failure` from 2026-09-26 onward, 0s
duration, zero jobs, zero check runs — while `Governance`, `Hypatia Security
Scan`, `Mirror to Git Forges`, `Secret Scanner` and `Workflow Security Linter`
all ran on the very same commits.

=== The second core matter: two gates that cannot both be satisfied

`Governance / Allowlist Preflight` runs `check-actions-policy.sh`, which reads
the repository's *live* Actions settings through the Administration API and
requires, among other things, `sha_pinning_required = true`.

This repository's workflows pin through `actions.lock` — readable refs in the
workflow, commit SHAs in the lock. That model is only viable while
`sha_pinning_required` is **off**: with it on, GitHub refuses a tag ref at
startup. The workflows run, therefore the setting is off, therefore the gate
fails. There is no file in this repository that can change that; it is a
repository setting reachable only with Administration write, which an Actions
`GITHUB_TOKEN` does not have.

This is a genuine policy conflict at the estate level, not a defect in this
repository, and pretending otherwise would produce a "fix" that cannot work.

=== The third core matter: a linter that fights the estate's own tooling

`Workflow Security Linter / lint-workflows` failed with exit code 14 because it
tested `head -1 "$f"` for `# SPDX-License-Identifier:`. `gh actions-lock`
*inserts* `# This workflow is managed by gh actions-lock.` at line 1 whenever it
mints or refreshes a lockfile, so the identifier is always on line 2 in a
managed repository. The check failed on all 14 workflow files at once, and
would re-fail on every future lockfile refresh.

The estate's governance bundle hit this exact fault first and fixed it in
`governance-reusable.yml`, with the reasoning recorded inline. This repository
carried a private copy of the *old* check, so the two gates disagreed about the
same tree.

=== The fourth core matter: a pinned reusable that predates its own fix

`Governance / Workflow security linter` failed at `Duplicate YAML keys in
workflows` — fixed above — which *unmasked* the next failure in the same job:
`Check SHA-pinned actions`.

That step runs:

----
gh extension install github/gh-actions-lock
bash scripts/update-actions-lock.sh --verify-local
----

`scripts/update-actions-lock.sh` exists in `hyperpolymath/standards`' own tree.
It does not exist in this repository, nor in `hyperpolymath/hypatia`, nor in any
other consumer checked. For a consumer the step dies with exit 127 before it
ever looks at a pin. It also demanded inline SHA pins *on top of* a lockfile —
the exact combination #74 had just dismantled.

This was never a green check. The `Governance` workflow has **171 recorded runs
and not one success** since it was introduced on 2026-05-17; the step simply
never got the chance to fail, because `Duplicate YAML keys` failed first.

Upstream has since fixed it. In `standards` today the step is gone from the
`Workflow security linter` job — *"the actions-lock gate used to be staged here
too. It is its own job now (`actions-lock-verify` …)"* — and the new
`check-actions-lock-gate.sh` states the actual policy plainly:

****
lockfile present → run the authoritative verifier and propagate its exit
status. … lockfile absent → RED: an unpinned `uses:` is a violation today,
lock or no lock.
****

So a present lockfile is sufficient on its own. Tag refs in the workflow are
the design, not a defect. The `Check SHA-pinned actions` step was enforcing a
policy the estate had already reversed.

The fix is therefore to stop pinning a revision of `governance-reusable.yml`
that predates its own correction. All five `hyperpolymath/standards` reusable
pins in this repository moved `84355587` → `a9a3281d` (`standards`@main,
2026-10-04). The workflow-staleness gate confirms the new pin is a genuine
ancestor of `standards` HEAD and carries no known defect, and its advisory
notices named exactly this refresh for `hypatia-scan.yml` and `scorecard.yml`.

== Decision

. **`actions.lock` is authoritative for pins, and its agreement with the
  workflows is now enforced, not assumed.** The lockfile was reconciled
  (`github/codeql-action` v4.38.0 -> v4.38.2, commit
  `2892aa5e19bbd11bc0cff5427e3b750a04d9e3c2`), and
  `workflow-linter.yml` gained three checks that make drift unrepresentable:
  duplicate YAML keys, lockfile drift, and lockfile coverage. They reuse the
  estate's shared scripts from `hyperpolymath/standards` at a pinned SHA
  rather than re-implementing them here — the whole point of the shared
  governance bundle is to not carry per-repo copies of gates.

. **The SPDX check scans the leading comment block, not line 1.** This is the
  idiom `governance-reusable.yml` already uses, so the two gates now agree.

. **`rescript-deno-ci.yml` is deleted.** ReScript eradication and the semantic
  port to AffineScript completed in #56 (commits `7180409`, `e0494e6`);
  `src/WikiMain.res` became `src/WikiMain.affine`. The repository contains no
  `.ts`, `.js` or `.res` file, so `deno test` failed with "no test modules
  found" and `deno fmt --check` had nothing to format. Keeping the workflow
  meant keeping a permanently red check whose only subject no longer exists.
  Its `actions.lock` entries (`denoland/setup-deno`) are removed with it.

. **`generator-generic-ossf-slsa3-publish.yml` keeps its provenance job, with
  one entry per key.** The duplicated `actions:`/`contents:` pair is merged
  (`write` subsumes `read`), so the job's effective permission set is
  unchanged. The stock `artifact1`/`artifact2` build step is left as the
  upstream template ships it and is flagged as an owner follow-up — see
  "Consequences".

. **The five `hyperpolymath/standards` reusable pins move `84355587` →
  `a9a3281d`.** This is the estate's own propagation action, not a local
  invention: the staleness gate's advisory notices named the refresh, and the
  newer revision is where the caller-tree `update-actions-lock.sh` bug and the
  "inline SHA pins *and* a lockfile" contradiction were both removed. See "The
  fourth core matter" above.

. **A weekly sweep is added to `workflow-linter.yml`.** Drift is not only
  introduced by editing a workflow file; an action bump merged from a branch
  that does not touch `.github/workflows/**` leaves the tree inconsistent
  until the next edit, which can be months.

== Consequences

. **Positive**: `CodeQL Advanced` runs again. Its last successful run was
  2026-09-22 (run 203); every run since 2026-09-26 died at startup with no
  diagnostic of any kind.
. **Positive**: the SLSA workflow becomes *valid*, so GitHub stops minting a
  phantom `failure` run against `.github/workflows/generator-generic-ossf-slsa3-publish.yml`
  on every push to `main`. Those runs carried the filename as the workflow
  name and the message "This run likely failed because of a workflow file
  issue" — the only visible trace of the duplicate keys.
. **Positive**: `Governance / Workflow security linter` now has a route to
  green. Its `Check SHA-pinned actions` step was unreachable for any consumer
  repo, and the `Governance` workflow had 171 runs and zero successes before
  this change.
. **Negative**: the pin bump brings three new governance jobs with it —
  `UUID v7 conformance`, `Live Actions policy (credentialed advisory)` and
  `Actions lockfile verify`. The first passes on this tree (verified locally
  with `check-uuid-v7.sh`). The second fails for the same repository-setting
  reason as `Allowlist Preflight`, so it is a duplicate of a known red rather
  than a new class of fault. The third runs `gh actions-lock --verify-local`
  against the reconciled lockfile; if the tool disagrees with the hand edit,
  that is a real finding about the lockfile and must be fixed, not hidden.
. **Positive**: the fault class is now caught *before* merge. A dependabot PR
  that bumps an action without regenerating the lockfile goes red on
  `lint-workflows` instead of silently killing a workflow after merge.
. **Negative**: dependabot PRs that bump an action will be red until the
  lockfile is regenerated. This is deliberate. The alternative — letting the
  bump through — is what produced this issue.
. **Negative**: `workflow-linter.yml` now fetches two scripts from
  `hyperpolymath/standards` at a pinned SHA. That pin is not tracked by the
  workflow-staleness gate (it is a `repository:`/`ref:` checkout, not a
  `uses:`), so it needs a human to bump it. Recorded here so it is not a
  surprise.
. **Open, owner action required**: `Governance / Allowlist Preflight` cannot
  be made green from inside the repository. It needs one of two things, and
  neither is a file in this repository: either `sha_pinning_required` is turned
  **on** at the repository level and every ref is pinned to a full-length SHA
  (in which case `actions.lock` becomes redundant and should be removed), or
  the gate in `standards` is relaxed to accept this repository's
  lockfile-based pinning.
. **Open, owner action required**: the SLSA workflow's build step is still the
  upstream template's placeholder (`echo "artifact1" > artifact1`). It has
  never run for real — the repository has no releases and no tags — but once it
  does, it would attach provenance for two meaningless files to the release.
. **Open, owner action required**: `SonarCloud Code Analysis` is red on `main`
  with "Quality Gate failed". It is produced by the SonarCloud GitHub App, is
  configured entirely outside this repository (there is no
  `sonar-project.properties` in the tree), and is out of scope for #81, which
  enumerates the checks it covers. Noted here so it is not lost.
. **Observation, not a fault**: `Governance / Guix packaging policy (Nix
  retired)` is currently green for the wrong reason. The job copies only
  `check-package-policy.sh` out of `standards`, so the capability resolver
  `check-rsr-profile.sh` is absent in CI; the script then treats this
  repository as declaring no packaging capability and reports "not
  applicable". If `standards` later ships the resolver alongside the checker,
  this repository will need either a `.machine_readable/rsr-profile.a2ml` or a
  real packaging artefact. Worth knowing before it happens.

== Alternatives considered

. **Pin everything to full-length SHAs and delete `actions.lock`.** Rejected.
  `cfc1b50` explicitly reverted that shape, the estate's own tooling
  (`gh actions-lock`) generates readable-ref-plus-lock, and it would not by
  itself satisfy the live-policy gate, which reads a repository setting.
. **Turn off `workflow-linter.yml`'s SPDX check.** Rejected. The identifier is
  worth checking; the check was wrong, not the requirement.
. **Delete `generator-generic-ossf-slsa3-publish.yml`.** Rejected as too
  aggressive: provenance on release is a real supply-chain control, and the
  defect was two duplicated keys, not the workflow's purpose. Deferred to the
  owner instead, per the placeholder note above.
. **Delete `codeql.yml` because the repository has no JavaScript.** Rejected.
  `javascript-typescript` with `build-mode: none` is cheap and covers
  `scripts/build-site.mjs`; removing analysis to make a check go green is the
  wrong direction. (The "missing language" hypothesis was tested and rejected:
  the action's `init/action.yml` is byte-identical across v4.38.0/v4.38.1/v4.38.2,
  and the failure predates any language-detection change.)
. **Leave `Allowlist Preflight` undocumented.** Rejected — #81's acceptance
  criteria explicitly allow a documented, owner-accepted red, and an
  undocumented red is indistinguishable from an unnoticed one.
